Step 0 — Pre-flight Checks

What this step does Verifies your environment is ready before any LLM call. Four checks are run: server reachability, model availability, Python dependencies, and output directory write-access. Fix every FAIL before proceeding.
Environment requirements

The pipeline needs a running llama.cpp server with an OpenAI-compatible API. Start it in a separate terminal:

# start llama.cpp (adjust path and model as needed) llama serve --fim-qwen-3b-default -ngl 99 --port 8012

Then click Run checks to verify all four requirements.

Step 1 — Configuration

What to do here Review and update your .agentconfig.yaml and .env settings. Changes are saved directly to disk. The most important fields are:
  • LLAMA_HOST — URL of your llama.cpp server
  • max_retries — how many times the pipeline retries on failure
  • coverage_threshold — minimum test coverage % to pass review
  • mode — auto picks the best loaded model; manual uses the names below

Step 2 — Feature Spec (PRD + TDD)

What to do here Create or edit the spec files for the feature you want to build. The pipeline needs two files in specs/<feature_name>/:
  • prd.md — Product Requirements Document. Use the ## Acceptance Criteria section — the validator LLM checks every numbered criterion against the TDD.
  • tdd.yaml — Test-Driven Design plan. Each test case maps to a pytest test the Developer Agent must write. Required keys: id, name, description, inputs, expected_result, expected_exception.
Click Load template to start from a blank template, or pick an existing feature from the dropdown.

Step 3 — Run Pipeline

What happens when you click Run The server launches python -m tools.agent_runner <feature> --skip-preflight as a real subprocess and streams its stdout/stderr here line-by-line via Server-Sent Events. The pipeline runs these stages in order:
  1. Spec validation — LLM checks PRD ↔ TDD consistency
  2. Code generation — Developer Agent writes src/ + tests/
  3. Guardrail scan — static + semantic security check
  4. Review + pytest — tests run, coverage measured, LLM verdict issued
  5. Retry loop — up to max_retries attempts if review fails
Enable Wizard mode to get structured diagnostics on every failure.

Step 4 — Run History

Where this data comes from Every pipeline run appends a JSON entry to logs/pipeline_runs.jsonl via wizard.append_run_log(). Each entry records timestamp, feature name, completed stages, any failure events, and the final status.

Step 5 — Log Viewer

What you're seeing The last 200 lines of logs/agent_runner.log — the same file that agent_runner.py writes to via Python's logging module. Use Refresh after a pipeline run to see new entries.
